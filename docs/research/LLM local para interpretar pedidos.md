# LLM local para interpretar pedidos

> **Relatório de pesquisa técnica** · Data de criação: 2026-11-23 · Sessão: S07 · Versão: 1.0
> **Escopo:** pesquisa técnica para o M5 (interpretação do pedido em português: parser de regras e depois LLM local, offline, sem API paga). O LLM só interpreta o texto e preenche o JSON validado `Request` (cômodos `{id, type, target_area_m2}`, relações `{a, b, kind near|far, intensity 1..5}`, `site`, `window_rule`) e nunca toca a geometria. **Não é o design do M5**, que será feito no brainstorming com o responsável. Este documento só reúne evidências, opções e propostas.
> **Base:** seis notas em `notes/LLM local para interpretar pedidos/`: [motores locais](notes/LLM%20local%20para%20interpretar%20pedidos/motores-locais.md), [modelos em português](notes/LLM%20local%20para%20interpretar%20pedidos/modelos-em-portugues.md), [saída estruturada](notes/LLM%20local%20para%20interpretar%20pedidos/saida-estruturada.md), [parser de regras](notes/LLM%20local%20para%20interpretar%20pedidos/parser-de-regras.md), [avaliação com casos de teste](notes/LLM%20local%20para%20interpretar%20pedidos/avaliacao-com-casos-de-teste.md), [requisitos de hardware](notes/LLM%20local%20para%20interpretar%20pedidos/requisitos-de-hardware.md).
> **Como ler os rótulos:** **[FATO]** = verificado em fonte citada (documentação, código-fonte, PyPI/GitHub, artigo, card do modelo) ou **medido** (nesta máquina ou em teste local reproduzível das notas). **[HIPÓTESE]** = inferência ou estimativa a confirmar. **[OPINIÃO]** = juízo de projeto do pesquisador. Versões e datas foram lidas em 2026-11-22/23. **Nenhum modelo foi baixado nem executado nesta máquina: toda latência atribuída a ela é estimativa.**

A pilha que as evidências apontam para o M5 é curta: **parser de regras em Python puro → esquema "delta" gerado por pedido → `llama-server` do llama.cpp com restrição por JSON Schema → validação Pydantic → reparo determinístico → fallback "só regras"**, sem nenhuma dependência Python nova no primeiro corte. O motor de referência é o llama.cpp (MIT, zips oficiais para Windows com CPU e Vulkan, servidor compatível com a OpenAI, restrição por gramática), e o Ollama, que hoje roda o próprio `llama-server` por baixo, só acrescenta conveniência. A família de modelos mais forte em tamanho pequeno e com licença Apache-2.0 é a **Qwen3.5**: o 4B lidera em seguir instruções (IFEval 89,8) e o 2B cai bastante (61,2 sem raciocínio). O gargalo, porém, é esta máquina. Ela tem 7,7 GB de RAM visível, soldada, e só 0,6 GB livres no momento da medição. Pelas estimativas, um 2B quente leva **~10 a 20 s** por pedido e ocupa ~1,6 a 1,8 GB; um 4B leva **~21 a 42 s** e ocupa ~2,4 a 3,5 GB, com risco real de paginação. Por isso o critério do design "responde em segundos" não se cumpre como está escrito e precisa virar um número. A decisão entre 2B e 4B não sai de leitura: sai de um **spike de medição local** de meio dia e de um **conjunto próprio de ~100 a 150 pedidos com gabarito JSON**, porque nenhum leaderboard público mede extração estruturada em português.

## O `llama-server` do llama.cpp é o motor de entrega, e o Ollama só acrescenta conveniência

### llama.cpp: maduro, MIT, com zips Windows prontos e restrição de saída embutida

**[FATO]** O llama.cpp publica várias builds por dia (a `b12635` saiu em 2026-11-22, e só nesse dia saíram pelo menos 10). A licença é MIT, e cada build traz zips Windows x64 para **CPU, Vulkan, SYCL e OpenVINO** ([GitHub releases](https://github.com/ggml-org/llama.cpp/releases); [API GitHub](https://api.github.com/repos/ggml-org/llama.cpp)). O `llama-server` oferece "OpenAI API compatible chat completions" e restringe a saída pelo campo `json_schema` ou por gramática GBNF. Ele escuta por padrão em 127.0.0.1, tem `--offline` ("forces use of the cache and blocks network access") e `--sleep-idle-seconds`, que descarrega o modelo e o cache KV depois de um tempo ocioso ([README do server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). A tabela de opções diz "port to listen (default: 9931)", depois de anos com 8080, então o app deve sempre passar `--port` explícito ([README raw](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)). **[HIPÓTESE]** A cadência diária obriga a **fixar uma build** no app em vez de seguir a "latest".

**[FATO]** O binding Python `llama-cpp-python` está ativo (0.3.37 em 2026-11-15, MIT), mas no PyPI só publica **sdist**, o que exige compilar C++ no Windows. As wheels `py3-none-win_amd64` vêm de um índice próprio (`abetlen.github.io/.../whl/cpu`), que chegava à 0.3.36 ([PyPI](https://pypi.org/pypi/llama-cpp-python/json); [índice whl/cpu](https://abetlen.github.io/llama-cpp-python/whl/cpu/llama-cpp-python/)). **[OPINIÃO]** Rodar no mesmo processo evita porta e processo extra, mas um crash nativo (de driver Vulkan, por exemplo) derrubaria o servidor Starlette inteiro, e a instalação dependeria de um índice fora do PyPI. O `llama-server` como subprocesso isola falhas e usa o binário oficial.

### Ollama: ótimo para trocar de modelo, mas não acrescenta capacidade de restrição

**[FATO]** O Ollama v0.40.17 (2026-11-10, MIT) roda no Windows como app em segundo plano, com API em `localhost:11434`, modelos em `%HOMEPATH%\.ollama` e pelo menos 4 GB de disco só para os binários ([docs Windows](https://docs.ollama.com/windows)). A doc de GPU diz que "Vulkan is enabled by default when the backend is installed" ([docs GPU](https://docs.ollama.com/gpu)), e a v0.40.17 corrigiu falhas de carga em iGPUs com memória compartilhada no Windows ([releases](https://github.com/ollama/ollama/releases)). Ainda assim, a página Windows só cita NVIDIA e AMD, e nenhuma fonte confirma que a Iris Xe é detectada (a nota de hardware também não achou menção a Vulkan no FAQ). A saída estruturada aceita `format` com um JSON Schema, no padrão `Model.model_json_schema()` → `model_validate_json` ([structured outputs](https://docs.ollama.com/capabilities/structured-outputs)). O ponto decisivo está no código: no branch `main`, "All GGUF models are served via the upstream llama-server subprocess", e o esquema é repassado ao campo `json_schema` do `llama-server` ([llm/server.go](https://raw.githubusercontent.com/ollama/ollama/main/llm/server.go); [llm/llama_server.go](https://raw.githubusercontent.com/ollama/ollama/main/llm/llama_server.go)). Ou seja, o Ollama **herda os mesmos limites de JSON Schema do llama.cpp**. Não foi confirmado qual release estável já traz esse arranjo.

**[OPINIÃO]** O Ollama vale pela troca rápida de modelos e pelo cliente pronto, mas tira do app o controle da versão do motor, que muda várias vezes por semana. A nota de avaliação acrescenta outro argumento: a API do Ollama só promete reprodutibilidade via `seed` e não documenta cache, slots, threads e lote ([Ollama API](https://docs.ollama.com/api/generate)). O `llama-server` direto expõe `--parallel 1`, `cache_prompt: false`, threads e lote. As duas notas divergem no papel do Ollama: a de motores o propõe para o desenvolvimento, e a de avaliação prefere o `llama-server` para medir. Como os dois falam HTTP compatível com OpenAI, um adaptador fino resolve a escolha sem tocar o resto do código. Essa escolha fica como pergunta ao responsável.

### Os leaderboards de português medem múltipla escolha, não extração

**[FATO]** O Open Portuguese LLM Leaderboard tem 9 tarefas PT-BR, quase todas de múltipla escolha ou classificação (ENEM, OAB, ASSIN2…) ([pt_config.yaml](https://huggingface.co/spaces/eduagarcia/open_pt_llm_leaderboard/raw/07a1890fc6f2b4a28fd81f60da58146fdd39af47/tasks_config/pt_config.yaml)). Um artigo do STIL 2026 mostrou três variantes do Qwen3-1.7B com médias a menos de 1 ponto uma da outra e perfis bem diferentes por categoria ([ACL Anthology](https://aclanthology.org/2026.stil-1.18/)). A nota de modelos não encontrou nenhum relato publicado de LLM ≤ 8B fazendo slot-filling para JSON em PT-BR. **[OPINIÃO]** Um bom ENEM não garante mapear "cantinho pra costura" para um tipo do catálogo nem "bem longe" para intensidade 4 ou 5. Só um conjunto de teste próprio decide, e essa lacuna é também uma contribuição original de portfólio.

### O raciocínio tem de ser desligado no template

**[FATO]** O Qwen3.5-4B opera "in thinking mode by default" e **não aceita** mais `/think` e `/nothink`: desliga-se com `"chat_template_kwargs": {"enable_thinking": False}`. O 2B já vem sem raciocínio ([Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B); [Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B)). No Gemma 4, o raciocínio só liga com o token `<|think|>` no system prompt. No SmolLM3, o BFCL e o IFEval **caem** com o raciocínio ligado (92,3 → 88,8 e 76,7 → 71,2) ([SmolLM3](https://huggingface.co/HuggingFaceTB/SmolLM3-3B)). **[OPINIÃO]** Em CPU, centenas de tokens de raciocínio multiplicam a latência. **[HIPÓTESE]** O único caso em que vale medir o raciocínio ligado é o Qwen3.5-2B, cujo IFEval sobe de 61,2 para 78,6.

## A gramática garante a sintaxe, e o Pydantic continua julgando o sentido

### O esquema delta do PyGridPlan cabe no subconjunto que o llama.cpp suporta

**[FATO]** O llama.cpp converte um **subconjunto** de JSON Schema em GBNF, e o que não suporta é "skipped silently". Funcionam `enum`, `required`, `minItems`/`maxItems`, `minLength`/`maxLength`, limites em `integer` e `$ref` local de um nível. Não funcionam limites em `number`, `$ref` aninhado, `anyOf`/`oneOf` misturado com `properties`, `uniqueItems`, `not` e condicionais. `additionalProperties` assume `false` por padrão ([grammars/README.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/grammars/README.md)). O mesmo documento avisa: "The JSON schema is only used to constrain the model output and is not injected into the prompt", então o esquema precisa ser descrito no prompt. A doc do Ollama também recomenda pôr o esquema no prompt e usar temperatura 0 ([Ollama](https://docs.ollama.com/capabilities/structured-outputs)).

**[FATO, teste local da nota]** Com o pydantic 2.14.3 do venv do projeto, um modelo gerado em tempo de execução com `create_model` e `Literal[tupla_de_ids]` produz um esquema que usa só `enum` para `a` e `b`, `enum` para `kind`, `minimum`/`maximum` em `integer` para `intensity`, `$ref` de um nível, `maxItems` e `additionalProperties: false`, **tudo dentro do subconjunto suportado** (conferido contra o [grammars/README.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/grammars/README.md)). Na prática, uma relação só consegue citar ids que existem no pedido. **[FATO]** Já o `Request` atual tem `target_area_m2: float | None = Field(default=None, gt=0)` ([request.py](../../src/pygridplan/model/request.py)). O `| None` vira `anyOf`, e o `gt=0` vira `exclusiveMinimum` em `number`, que a gramática não aplica ([grammars/README.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/grammars/README.md)). **[OPINIÃO]** É mais um motivo para o LLM preencher um esquema delta próprio, raso, em vez do `Request` inteiro. As regras sugeridas são: nada de `number` com limites, nada de `X | None` desnecessário, `maxItems` em toda lista, `maxLength` em toda string livre e `extra="forbid"`.

**[FATO]** Compilar a gramática custa ~0,05 s no llama.cpp em esquemas reais de porte médio, mas a amostragem restrita subiu o tempo por token de 15,40 ms para 29,98 ms com o Llama-3.1-8B no backend llama.cpp ([JSONSchemaBench](https://arxiv.org/html/2501.10868v3)). **[HIPÓTESE]** No i5 com modelo de 1 a 4B, o peso relativo desse custo deve ser menor, porque o modelo domina o tempo. Precisa de medição. **[FATO]** O llguidance existe no llama.cpp desde a build b4613, mas só com `-DLLAMA_LLGUIDANCE=ON`, que exige Rust ([docs/llguidance.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/llguidance.md)). Não foi verificado se os zips oficiais vêm com ele ligado. **[HIPÓTESE]** O conversor nativo parece reordenar as propriedades, com as `required` antes das opcionais. Um campo de raciocínio opcional poderia acabar depois da resposta, então, se existir, deve ser `required` e o primeiro.

### A restrição não piora a acurácia, mas em modelos pequenos não garante o sentido

**[FATO]** No JSONSchemaBench, com Llama-3.1-8B, todos os motores restritos ficaram acima do baseline sem restrição (GSM8K: só o LM 80,1; llama.cpp 82,4). A cobertura empírica do llama.cpp foi 0,95 contra 0,90 do LM sozinho ([JSONSchemaBench](https://arxiv.org/html/2501.10868v3)). A dottxt atribuiu o resultado negativo de Tam et al. (2024) a prompts inconsistentes, e recomenda o mesmo prompt nos dois modos, um exemplo no formato exato e o esquema descrito no prompt ([blog dottxt](https://blog.dottxt.ai/say-what-you-mean.html)). Por outro lado, o StructureBench (IJCAI 2026), sobre modelos on-device de 0,5 a 8B, resume que a restrição "guarantees syntactic validity, it does not necessarily improve semantic accuracy; smaller models may degenerate under complex grammars" ([IJCAI 2026](https://www.ijcai.org/proceedings/2026/0267.pdf)). "The Constraint Tax" aponta que, abaixo de 3B, o próprio esquema pode virar "a material part of the generation problem" ([arXiv 2605.26128](https://arxiv.org/pdf/2605.26128)). Desses dois só os resumos foram lidos.

**[OPINIÃO]** O que a gramática não cobre fica com o Pydantic: autorrelação, par repetido e coerência com o texto (o `model_validator` do `Request` já rejeita os três primeiros casos). O laço sugerido tem seis passos: (1) gerar com o esquema dinâmico; (2) `Delta.model_validate_json`; (3) mesclar no `Request` e rodar o validador existente; (4) **reparo determinístico primeiro** (descartar duplicadas e autorrelações, com aviso); (5) **no máximo uma** retentativa com o erro no prompt; (6) fallback "só regras" com aviso ao usuário. **[HIPÓTESE]** JSON truncado e laços de espaço em branco se evitam com `maxItems`, `maxLength` e um `max_tokens` calculado a partir deles. **[OPINIÃO]** JSON Schema em `response_format` é mais simples que tool calling: não depende do template de ferramentas de cada família de modelo. **[FATO]** Em tool calling, o llama.cpp injeta o esquema no prompt; em `json_schema`, não ([grammars/README.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/grammars/README.md)).

**[OPINIÃO]** Nenhuma biblioteca nova entra no primeiro corte. A restrição nativa do llama.cpp ou do Ollama cobre o esquema delta, e o Pydantic já é dependência. O Instructor só valeria pela retentativa, que são ~15 linhas escritas à mão. O Outlines (`<3.14`) prenderia o projeto ao llama-cpp-python e compila gramáticas em segundos (3,48 s contra 0,05 s no JSONSchemaBench). **[HIPÓTESE]** O cliente HTTP do `llama-server` pode ser a biblioteca padrão. Só os binários do llama.cpp e o arquivo GGUF entram, e ficam fora do git.

## O parser de regras resolve o vocabulário fechado e decide quando chamar o LLM

### A biblioteca padrão basta, e o text2num destrói a palavra "quarto"

**[OPINIÃO]** Para ~23 tipos de cômodo, medidas e relações, bastam `unicodedata` + `re` + uma tabela de sinônimos versionada em `data/`, com `rapidfuzz` opcional só para erros de digitação. **[FATO, teste local da nota]** O `rapidfuzz` 3.14.6 (MIT) acertou "banhero" → `banheiro` (93,3) e "cosinha" → `cozinha` (85,7). Também casou "sala" com `sala de estar` com nota 90 (por casamento parcial) e deu só 60 para "vaga" → `garagem`: **o fuzzy corrige grafia, não resolve sinônimos** ([PyPI rapidfuzz](https://pypi.org/project/rapidfuzz/)). Por isso, se entrar, deve rodar depois do casamento exato e com corte alto (~85). As alternativas pesadas não compensam. **[FATO]** O modelo `pt_core_news_sm` do spaCy é CC BY-SA 4.0 e o NER segue o WikiNER (PER/LOC/ORG/MISC), sem rótulo de cômodo ([spaCy models/pt](https://spacy.io/models/pt)). O Unidecode é GPLv2+ ([PyPI](https://pypi.org/project/Unidecode/)). O Duckling é Haskell, roda como servidor HTTP e não tem dimensão de área para PT ([Dimensions/PT.hs](https://github.com/facebook/duckling/blob/main/Duckling/Dimensions/PT.hs)). O Recognizers-Text Python está em 1.0.2a2 desde 2019 ([PyPI](https://pypi.org/pypi/recognizers-text-suite/json)).

**[FATO, teste local da nota]** O `text2num` 3.1.0 (MIT, com suporte a pt-BR) converte bem os números por extenso ("doze vírgula cinco metros" → "12,5 metros"; "terreno de doze por trinta e cinco" → "12 por 35"). Mas troca **"quarto" pelo ordinal "4º" em qualquer contexto**: "casa com três quartos sendo uma suíte" vira "casa com 3 4ᵒˢ sendo uma suíte", e "quero um quarto" vira "quero 1 4º" ([PyPI text2num](https://pypi.org/project/text2num/)). **[OPINIÃO]** Num domínio em que "quarto" é o substantivo mais importante, esse é um bug grave e silencioso. O `alpha2digit` nunca pode rodar sobre o texto inteiro. Um léxico próprio de 0 a 100 mais "e meio/meia" cabe em ~40 linhas, e o text2num serve no máximo como oráculo em `tests/`.

### O catálogo não tem "suíte" nem "oficina", e o próprio design usa "oficina" como exemplo

**[FATO]** O `data/room_types.yaml` (v0.3) tem 23 ids, de `sala` a `garagem` ("Garagem (por vaga)"), mas **não tem `suite` nem `oficina`** ([room_types.yaml](../../data/room_types.yaml)). O exemplo canônico da seção 7 do design é justamente "oficina longe dos quartos" ([mvp.md §7](../design/mvp.md)). **[OPINIÃO]** "Suíte" deve virar uma **composição** (quarto + banheiro privativo), não um id. **[FATO, lido no código nesta síntese]** O catálogo já tem o campo `suite_access` (quarto → closet → banheiro, seção 5.5 do design), usado pelo validador de acesso e pelo gerador ([room_types.yaml](../../data/room_types.yaml); [access.py](../../src/pygridplan/validation/access.py)). Mas o `Request` não diz que **um banheiro específico** pertence a **um quarto específico**: ele tem só a lista de cômodos e relações near/far ([request.py](../../src/pygridplan/model/request.py)). **[HIPÓTESE]** A composição poderia virar quarto + banheiro + relação near de intensidade alta, deixando o `suite_access` liberar a passagem, mas isso não garante a suíte. Representar a suíte, e decidir o que fazer com "oficina", é decisão de modelo de dados e de catálogo, não do LLM.

**[OPINIÃO]** O léxico deve ser um YAML em `data/` (`type` → termos e plurais, com fonte por entrada), seguindo a trilha `Dn` do projeto. Termos criados pelo agente ficam marcados como `agente`, e o casamento é sempre pela expressão mais longa primeiro ("quarto de solteiro" antes de "quarto"). Alguns termos ambíguos pedem regra ou confirmação: "sala" sozinha, "WC" (banheiro ou lavabo?), "abrigo", "área" (de serviço, gourmet ou m²?). **[FATO]** O Rasa trata sinônimos como mapeamento **depois** da extração ([Rasa docs](https://legacy-docs-oss.rasa.com/docs/rasa/nlu-training-data/)).

### A intensidade 1..5 é decisão de projeto, não dado de literatura

**[FATO]** A nota não encontrou léxico pt-BR de intensificadores com escala numérica. A semântica de grau trata "muito" e "bem" de forma qualitativa ([Quadros Gomes 2011](https://revistas.gel.org.br/estudos-linguisticos/article/download/1403/943/3703)). **[OPINIÃO]** A nota propõe uma tabela versionada, com valores marcados como decisão (`agente` ou `responsável`). Exemplos: "colado/integrado com" → near 5; "perto" → near 3; "de preferência perto" → near 2; "longe" → far 3; "o mais longe possível" → far 5; "não quero perto" → far 3, porque a negação de near não equivale a um far forte. A fórmula seria `base + Δ intensificador − Δ atenuador`, limitada a [1, 5]. **[HIPÓTESE]** Como a intensidade é subjetiva, a "fonte" mais honesta é o responsável pontuar uns 30 exemplos.

### O padrão híbrido: regras primeiro, LLM só para o resíduo, regras com precedência

**[FATO]** No Rasa Pro ≥ 3.12, NLU e LLM preenchem slots no mesmo turno. "The NLU based mapping takes higher priority", e "the LLM is not allowed to correct NLU-filled slots" por padrão, com `allow_nlu_correction: true` como opção ([Rasa docs: Slots](https://rasa.com/docs/reference/primitives/slots/)). Quando o LLM falha, a mensagem cai para o NLU ([coexistence routers](https://rasa.com/docs/reference/config/components/coexistence-routers/)). **[FATO]** O pacote `rasa` aberto está em 3.6.21 e exige Python < 3.11, incompatível com o 3.13 do projeto ([PyPI](https://pypi.org/pypi/rasa/json)). Só o padrão serve, não a biblioteca.

**[OPINIÃO]** Contrato sugerido, coerente com a seção 7 do design:

1. `parse_rules(texto)` devolve o `Request` parcial, os spans cobertos e as ambiguidades, sem LLM.
2. O **resíduo** (trechos não cobertos com palavra de conteúdo) decide se o LLM é chamado. Sem resíduo, não há chamada: zero latência e zero alucinação.
3. O LLM recebe o texto, os slots já preenchidos ("não altere"), os ids com rótulos e o resíduo destacado, e devolve **só o delta**.
4. No merge, as regras têm precedência, e uma tentativa do LLM de mudar um slot das regras vira **conflito mostrado**, não sobrescrita.
5. Toda inferência do LLM vira premissa editável com origem (`regra` | `llm` | `padrão`) e o trecho que a gerou.

Sem LLM instalado, o resíduo aparece como "não interpretado". As regras param em escopo longo: negação coordenada ("nem a cozinha nem a lavanderia perto dos quartos"), correferência ("ela", "esse quarto") e quantidades compostas ("3 quartos sendo uma suíte" é inclusão; "3 quartos e 1 suíte" é ambíguo). Esses casos vão ao LLM ou à confirmação.

## Cem a 150 casos com gabarito JSON e um scorer próprio bastam para escolher o modelo

### O tamanho do conjunto define que diferença dá para enxergar

**[FATO, calculado na nota]** Com n = 100 e acurácia observada de 0,80, o intervalo de Wilson 95% é 0,711 a 0,867 (±7,8 pp). Com n = 50, é ±10,9 pp ([statsmodels proportion_confint](https://www.statsmodels.org/stable/generated/statsmodels.stats.proportion.proportion_confint.html)). Para comparar dois modelos ou prompts no mesmo conjunto, o teste certo é o **McNemar exato**, que só olha os casos discordantes ([statsmodels mcnemar](https://www.statsmodels.org/stable/generated/statsmodels.stats.contingency_tables.mcnemar.html)). Com b = 15 e c = 5, p ≈ 0,041. Com b = 10 e c = 3, p ≈ 0,092. Ou seja, mesmo com 100 casos é preciso uma vantagem líquida de ~10 casos. **[FATO]** A Anthropic recomenda diferenças pareadas e erros padrão clusterizados quando as questões não são independentes ([Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals)). Hamel Husain recomenda começar com ~100 exemplos e reservar um split de teste ([LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)).

**[OPINIÃO]** A meta é **~100 a 150 casos de desenvolvimento e ~50 de teste reservado**, com o split atribuído por **pedido-semente** (todas as paráfrases de uma semente no mesmo split). Os casos cobrem 12 fenômenos marcados por tag: base, paráfrase, coloquial/regional, digitação/sem acento, números por extenso, negação, intensidade, quantidade, fora de escopo, conflito, injeção e pedido mínimo. As sementes e os casos difíceis são escritos à mão. Paráfrases geradas por modelo maior são revisadas, marcadas com `source` e nunca entram no split de teste nem como few-shot.

### Métricas por emparelhamento, sem juiz LLM

**[OPINIÃO]** Os ids de cômodo são arbitrários, então a comparação não pode ser por igualdade de string. Primeiro se emparelham os cômodos por tipo (e por área, com atribuição ótima quando há vários do mesmo tipo). Depois se reescrevem as relações em termos do gabarito e se comparam como conjuntos não ordenados. As métricas vão em camadas: taxa de esquema válido (perto de 100% com restrição; abaixo disso é bug de integração), **acerto exato por pedido** (a métrica binária que alimenta Wilson e McNemar), P/R/F1 de cômodos e relações, MAE e acerto ±1 de intensidade, alucinação, abstenção correta em fora de escopo, latência p50/p95 e RAM de pico. **[FATO]** Hamel recomenda asserções de código antes de juiz LLM e rótulos binários ([LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). **[OPINIÃO]** Com gabarito JSON, um juiz só acrescentaria custo e não determinismo. A comparação **regras sozinhas × LLM sozinho × regras + LLM** no mesmo conjunto é o que justifica, ou não, ter o LLM no portfólio.

### Determinismo exige configuração, e a avaliação lenta fica fora da suíte padrão

**[FATO]** No `llama-server`, `cache_prompt` (padrão `true`) "pode causar resultados não determinísticos", `seed` tem padrão −1, e há relatos de saídas diferentes com cache, Vulkan, offload para GPU e decodificação especulativa ([README do server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); [#2838](https://github.com/ggml-org/llama.cpp/issues/2838); [#19981](https://github.com/ggml-org/llama.cpp/issues/19981); [#4020](https://github.com/ggml-org/llama.cpp/discussions/4020)). Os resumos dessas issues vieram de snippets de busca. **[OPINIÃO]** Configuração de avaliação: CPU, build fixada, `--parallel 1`, `cache_prompt: false`, temperatura 0, `seed` fixo, threads e lote registrados, um caso por vez. **[HIPÓTESE]** Assim as execuções repetidas devem bater, e isso tem de ser medido rodando 2 ou 3 vezes. **[OPINIÃO]** A suíte padrão roda regras, validação dos gabaritos, scorer e o caminho do LLM com respostas gravadas. A avaliação com modelo real fica em `@pytest.mark.llm_eval`, desligada por padrão, grava relatório em `out/` e compara com uma baseline. Cada relatório registra `dataset_sha256`, `prompt_sha256`, o arquivo e o hash do GGUF, a quantização, a build, os parâmetros e o hardware. Um scorer próprio de ~100 a 200 linhas em pytest basta. O Inspect AI (MIT, Python ≥ 3.11, suporta Ollama e llama-cpp-python) é o framework a reavaliar se a avaliação crescer ([PyPI inspect-ai](https://pypi.org/project/inspect-ai/)).

## Nesta máquina, um 2B quente leva ~10 a 20 s, e "responde em segundos" não se cumpre

### O que foi medido nesta máquina e o que vem de máquinas parecidas

**[FATO, medido localmente pelo coordenador em 2026-11-22, PowerShell/CIM]** Samsung 750XGK com Windows 11 Home. Intel Core i5-1335U: 10 núcleos (2P + 8E), 12 threads, L2 de 6,5 MB, L3 de 12 MB. **7,7 GB de RAM visível** (8 × 1 GB LPDDR4x-4267, soldada), pagefile de 15 GB, e **só 0,6 GB livres** no momento da medição, com outros apps e sessões paralelas abertos. GPU Intel Iris Xe integrada (memória compartilhada), com runtime Vulkan presente e **sem NVIDIA/CUDA**. ~205 GB livres no C:, Python 3.13. **Ollama e llama.cpp não estão instalados.** O suporte a AVX-VNNI **não foi medido**: o pedido às pesquisas o citou por conhecimento prévio, e a página da Intel não o lista. Falta conferir localmente (por exemplo, com o Coreinfo da Sysinternals). **[FATO]** A Intel ARK lista 80 EU na Iris Xe deste chip e no máximo 2 canais de memória ([Intel ARK](https://www.intel.com/content/www/us/en/products/sku/232153/intel-core-i51335u-processor-12m-cache-up-to-4-60-ghz/specifications.html)). A banda teórica com LPDDR4X-4266 é de 68,2 GB/s ([CPU-Monkey](https://www.cpu-monkey.com/en/cpu-intel_core_i5_1335u)).

**[FATO]** O dado mais próximo vem de uma **máquina-irmã** (750XGK com i7-1355U, Iris Xe de 96 EU, **Linux/Mesa**). Ali, o llama.cpp Vulkan rodou o **Qwen3.5-2B Q4_K_M** a **pp512 = 420,06 t/s, pp4096 = 338,60 t/s e tg128 = 21,98 t/s**, e a leitura de memória medida foi de 57,6 a 61,9 GB/s ([inferzero #76](https://github.com/rizagp/inferzero/issues/76)). Na Iris Xe do Tiger Lake, com Llama 2 7B Q4_0, o Vulkan deu 42,0/7,3 t/s (jan/2025) e depois 106,2/5,9, enquanto a CPU deu 30,5/9,9 e 73,3/5,2 ([llama.cpp #10879](https://github.com/ggml-org/llama.cpp/discussions/10879)). Ou seja, na Iris Xe o ganho do Vulkan aparece no prefill e quase some na geração. **[FATO]** Num Galaxy Book3 com o mesmo i5 (unidade NP750XFG), o chassi segura PL1 de 23 W e PL2 de 39 W ([Notebookcheck](https://www.notebookcheck.net/Samsung-Galaxy-Book3-review-The-Intel-Core-i5-1335U-celebrates-a-solid-premiere.723256.0.html)). **Não há benchmark publicado de llama.cpp só na CPU para este chip nem para equivalentes.** Os números de CPU abaixo são estimativas.

### Memória: 2B cabe com folga curta, 4B fica no limite, 7 a 9B não cabem

**[HIPÓTESE, nota de hardware]** Memória residente ≈ GGUF + KV + buffers. Os Qwen3.5 híbridos têm só 6 (no 0,8B/2B) ou 8 (no 4B/9B) camadas de atenção plena, então o KV em 4k de contexto fica em ~48 MiB no 2B e ~128 MiB no 4B (f16), calculado a partir dos `config.json` ([config 2B](https://huggingface.co/Qwen/Qwen3.5-2B/blob/main/config.json); [config 4B](https://huggingface.co/Qwen/Qwen3.5-4B/blob/main/config.json)). Estimativas: Qwen3.5-2B Q4_K_M com 4k ≈ **1,6 a 1,8 GB**; 3 a 4B ≈ **2,4 a 3,5 GB**; 7 a 9B ≈ 5 a 6,5 GB, inviável. Com Windows, navegador, app e um 4B, o total chega a ~6,5 a 8,5 GB dos 7,7 GB, o que traz **risco real de paginação**, coerente com os 0,6 GB livres medidos. **[HIPÓTESE]** Com Vulkan, os pesos são copiados para buffers de GPU na mesma RAM e podem ocupar até ~2 vezes o arquivo se as páginas mmap continuarem residentes. Isso pode inverter a escolha entre CPU e iGPU numa máquina de 8 GB.

**[FATO]** O fluxo do app já é sequencial (interpretar e depois resolver). O `llama-server` descarrega o modelo com `--sleep-idle-seconds` e recarrega no pedido seguinte, e o Ollama faz o mesmo com `keep_alive` ([README do server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); [Ollama FAQ](https://docs.ollama.com/faq)). **[HIPÓTESE]** Rodar o LLM junto com o CP-SAT seria ruim para os dois, porque disputam banda, núcleos e os 23 W. Descarregar antes do solve custa ~1 a 3 s de recarga e perde o cache do prefixo do prompt.

### Latência estimada: a geração domina, e encurtar o JSON é a alavanca mais forte

**[HIPÓTESE, nota de hardware; nada foi medido nesta máquina]** Latência ≈ carga (se frio) + 1.200 tokens de prompt ÷ pp + 200 tokens de saída ÷ tg, com modelo quente e sem cache de prefixo:

| Modelo Q4_K_M | Caminho | pp (t/s) | tg (t/s) | **Total quente** | RAM estimada |
|---|---|---|---|---|---|
| ~1,5B (Qwen2.5-1.5B) | CPU | 150 a 250 | 22 a 38 | **~10 a 17 s** | dentro da faixa 0,6 a 1,8 GB (0,8 a 2B) |
| Qwen3.5-2B | iGPU Vulkan | 280 a 350 | 18 a 22 | **~12 a 15 s** | ~1,6 a 1,8 GB (mais a cópia em buffer de GPU, a medir) |
| Qwen3.5-2B | CPU | 130 a 220 | 18 a 30 | **~12 a 20 s** | ~1,6 a 1,8 GB |
| 3B | CPU | 80 a 140 | 12 a 20 | **~19 a 32 s** | dentro da faixa 2,4 a 3,5 GB (3 a 4B) |
| Qwen3.5-4B / Qwen3-4B / Gemma-3-4B | iGPU Vulkan | 140 a 180 | 9 a 14 | **~21 a 31 s** | ~2,4 a 3,5 GB (mais buffer de GPU) |
| Qwen3.5-4B / Qwen3-4B / Gemma-3-4B | CPU | 60 a 100 | 9 a 15 | **~25 a 42 s** | ~2,4 a 3,5 GB |
| 7 a 8B | CPU ou iGPU | 30 a 90 | 5 a 8 | ~40 a 80 s | não cabe |

A coluna de RAM repete as faixas da nota de hardware por classe de tamanho (arquivo + KV + buffers); a nota não dá número próprio para o 1,5B nem para o 3B. **[HIPÓTESE]** Com cache de prefixo, o prefill cai para ~1 a 4 s em qualquer linha até 4B. Com saída de 100 tokens, a geração cai pela metade. Com o CP-SAT rodando junto, os tempos podem dobrar. **[HIPÓTESE, ligação entre as notas]** A arquitetura do M5 encurta a saída por construção: as regras preenchem cômodos, números e terreno, e o LLM devolve só o delta de relações, às vezes nada. Num pedido típico, a saída deve ficar bem abaixo dos 200 tokens da tabela, mas isso não foi medido.

### O critério "responde em segundos" precisa virar um número

**[FATO]** A seção 12 do design pede que o LLM "cabe em 8 GB junto com o resto, responde em segundos, preenche o JSON corretamente num conjunto de frases de teste" ([mvp.md §12](../design/mvp.md)). **[HIPÓTESE, nota de hardware]** Entendido como menos de 5 s, o critério **não é alcançável** com ~200 tokens de saída em nenhum tamanho útil, porque exigiria tg acima de 40 t/s. **[OPINIÃO]** O design precisa de um número explícito. A nota sugere **P50 quente ≤ 15 s** e RAM de pico abaixo de ~2 GB. Outra saída é medir com a saída real do esquema delta e só então fixar a meta. A decisão é do responsável.

### A tensão entre as notas: o 4B é o melhor, o 2B é o que cabe

As duas notas não se contradizem nos fatos. Elas otimizam coisas diferentes. A de modelos ordena por qualidade e sugere testar **Qwen3.5-4B (sem raciocínio) → Gemma 4 E2B → Qwen3.5-2B → SmolLM3-3B / Granite-4.0-Micro**. Ela se apoia no IFEval (89,8 contra 61,2) e estima o 4B em ~3 a 3,5 GB residentes, "viável, mas apertado". A de hardware estima o mesmo 4B em **~21 a 42 s** e chama a RAM de limítrofe, e por isso põe o alvo realista em **0,8 a 2B**. Há ainda um detalhe que a ordem por qualidade esconde: o GGUF Q4_K_M do **Gemma 4 E2B tem 3,11 GB, mais que o do Qwen3.5-4B (2,74 GB)**. **[HIPÓTESE]** As embeddings por camada do Gemma podem custar menos em RAM via mmap, mas isso precisa ser medido. Sem essa medição, o Gemma 4 E2B não é a opção "leve" que o nome sugere.

**[OPINIÃO]** Ordem de teste que respeita o hardware, em duas etapas:

1. **Velocidade e RAM primeiro (spike, sem qualidade):** Qwen3.5-0.8B, Qwen3.5-2B e Qwen3.5-4B em Q4_K_M (0,53 + 1,28 + 2,74 ≈ 4,6 GB de download), mais Gemma 4 E2B (3,11 GB) só se o responsável quiser medir o efeito do mmap. Ficar na mesma família isola o efeito do tamanho.
2. **Qualidade no conjunto dev:** começar pelo **Qwen3.5-2B sem raciocínio**, por ser o que cabe. Em seguida, o **Qwen3.5-4B com raciocínio desligado**, como teto de qualidade. Se o 2B passar na barra de qualidade, para aí. Se só o 4B passar, aceitar a latência maior com descarga antes do CP-SAT, ou testar o 2B com raciocínio ligado (o IFEval sobe para 78,6, à custa de latência). SmolLM3-3B, Granite-4.0-Micro e Gemma 4 E2B entram só se a família Qwen falhar nos casos específicos de português. O 0,8B fica como piso de velocidade, e o Tucano 2 fica fora até existir GGUF.

**[OPINIÃO]** O critério de decisão da nota de hardware é escolher o **menor modelo** que (a) acerte o JSON no conjunto de teste, (b) fique abaixo de ~2 GB de RAM de pico e (c) tenha P50 quente ≤ 15 s. Se o 2B falhar em (a), testar 3 a 4B e aceitar a latência.

### O spike de medição local é o que decide

**[OPINIÃO, nota de hardware]** O spike leva ~meio dia e usa os zips oficiais CPU e Vulkan da mesma build. Os passos: (1) varrer threads na CPU (`llama-bench -ngl 0 -t 2,4,6,8,10 -p 512 -n 128 -r 3`), porque com 2P + 8E usar todos os 12 threads pode piorar ([llama.cpp #572](https://github.com/ggerganov/llama.cpp/discussions/572)); (2) comparar CPU e Vulkan com `-pg 1200,200`; (3) subir o `llama-server` com `-c 4096 -np 1 --sleep-idle-seconds 60` e mandar 5 a 10 pedidos reais com o esquema delta, medindo latência, `PeakWorkingSet64` e falhas de página duras; (4) medir a recarga; (5) repetir com o CP-SAT rodando; (6) repetir três vezes seguidas e uma na bateria, por causa da térmica. Cada medição vai para uma planilha com modelo, quantização, backend, threads, pp, tg, RAM, latência fria/quente/com prefixo, JSON válido, modo de energia e build. **[FATO]** O comando de referência da comunidade é `llama-bench -m <modelo>.gguf -ngl 100 -fa 0,1` ([#10879](https://github.com/ggml-org/llama.cpp/discussions/10879)).

## Conclusão: o tamanho do modelo é a decisão cara, e o resto já tem resposta

A pesquisa reduziu o M5 a uma única incógnita real. O motor (`llama-server`), o formato (GGUF), a restrição (JSON Schema nativo), o validador (Pydantic, já no projeto) e a camada de regras (biblioteca padrão) têm resposta de baixo risco e não acrescentam dependência Python. O que fica aberto é o tamanho do modelo, e ele não se decide lendo: o melhor modelo em seguir instruções é o que esta máquina menos comporta. O desenho "regras primeiro, LLM só para o resíduo, só o delta" deixa de ser elegância e vira **a principal alavanca de desempenho**. Cada slot que as regras resolvem é um token a menos de geração, e cada pedido sem resíduo é uma chamada a menos.

Há também uma implicação de produto. Como nenhum benchmark público mede extração de pedidos de planta em português, o conjunto de teste com gabarito e a comparação "regras × LLM × regras + LLM" são ao mesmo tempo a ferramenta de decisão e a peça mais original do M5 para o portfólio. E duas decisões que parecem de IA são de dados: o catálogo sem "suíte" e "oficina" e a tabela de intensidade. Nenhum modelo, por maior que seja, preenche um tipo que o catálogo não tem.

## Lacunas e próximos experimentos

- **Nenhuma latência ou RAM desta máquina foi medida.** Faltam o spike com `llama-bench` e `llama-server` (CPU × Vulkan, threads, RAM de pico, recarga, convivência com o CP-SAT) e o desempenho do driver Vulkan da Intel **no Windows** (o dado da máquina-irmã é de Linux/Mesa).
- Não há benchmark publicado de llama.cpp só na CPU em i5-1335U ou chips de 15 W equivalentes.
- O esquema delta não foi convertido em GBNF localmente: a execução do conversor foi bloqueada pela política de permissões da sessão. O próximo passo é obter a gramática pelo `llama-server` (`response_fields: ["generation_settings/grammar"]`) e criar um teste de registro.
- Falta verificar se os zips oficiais do llama.cpp vêm com llguidance e se o `StructuredOutputConfig` do OpenVINO GenAI funciona em `GPU`.
- Falta confirmar se o Ollama no Windows detecta e usa a Iris Xe via Vulkan.
- Não há dados de qualidade dos candidatos em extração PT-BR. O conjunto de teste ainda não existe; o ponto de partida são os exemplos do `mvp.md` e sementes do responsável.
- Faltam o efeito do raciocínio ligado no Qwen3.5-2B, o efeito de um campo `raciocinio` no esquema e o idioma das chaves (pt × en). Nada disso tem evidência publicada para modelos de 1 a 4B.
- Falta glossário com fonte para sinônimos regionais de ambientes ("living", "edícula", "dependência"), o que pede uma trilha `Dn`.

## Perguntas que o responsável terá de decidir

1. **Motor no desenvolvimento:** `llama-server` direto desde o início ou Ollama? O `llama-server` dá controle de cache, slots e threads para uma avaliação reprodutível, e é o mesmo motor da entrega. O Ollama troca de modelo em segundos e tem cliente Python pronto, mas acrescenta um daemon que muda várias vezes por semana e documenta menos parâmetros.
2. **Motor na entrega:** `llama-server` como subprocesso (zip oficial fixado, isola crashes, nada a compilar), `llama-cpp-python` no mesmo processo (sem porta, mas índice fora do PyPI e crash nativo derruba o servidor) ou exigir o Ollama instalado (mais simples para o código, sem controle de versão)?
3. **Backend:** CPU como padrão, com o Vulkan só se o spike provar ganho sem estourar a RAM? Ou aceitar o Vulkan desde já, pelo prefill mais rápido, com o risco de driver e de cópia dupla dos pesos?
4. **Spike e downloads:** autorizar o spike de medição de ~meio dia e o download de **~4,6 GB** de modelos (Qwen3.5 0,8B, 2B e 4B), mais **3,11 GB** se o Gemma 4 E2B entrar, mais os zips do llama.cpp (tamanho não conferido)? Onde guardar: `%LOCALAPPDATA%\PyGridPlan\models\` ou `out/`, sempre fora do git e com SHA-256 registrado em `data/`? O spike exige fechar apps, porque a máquina tinha só 0,6 GB livres na medição.
5. **Ordem de teste dos modelos:** aceitar a ordem proposta (velocidade e RAM de 0,8B/2B/4B primeiro; qualidade começando pelo 2B, com o 4B como teto) ou seguir a ordem por qualidade da nota de modelos (4B primeiro)? Incluir o Gemma 4 E2B, cujo arquivo é maior que o do 4B?
6. **Meta de latência e de RAM:** que número substitui "responde em segundos" na seção 12 do design? A sugestão é P50 quente ≤ 15 s e RAM de pico ≤ ~2 GB, com P95 a definir. Também é possível fixar a meta só depois de medir a saída real do esquema delta.
7. **Escopo do LLM:** só o delta (relações e intensidades, talvez `window_rule`), com cômodos e números sempre vindos das regras? Ou o LLM também pode criar cômodos e escolher tipos do catálogo? Isso muda o tamanho da saída (latência) e o enum do esquema.
8. **O LLM pode corrigir slots das regras?** O padrão do Rasa ≥ 3.12 é "não", e o conflito vira pergunta ao usuário. Permitir aumenta a cobertura de erros das regras, mas reabre a porta para alucinação sobre fatos explícitos.
9. **"Suíte" e "oficina":** acrescentar ao catálogo `data/room_types.yaml`, tratar a suíte como composição (quarto + banheiro privativo) ou mapear "oficina" para o tipo mais próximo com confirmação? O catálogo já permite passar do quarto ao banheiro (`suite_access`), mas o `Request` não sabe dizer que um banheiro específico pertence a um quarto específico. Uma suíte garantida exige mudar o modelo de dados.
10. **Léxico como trilha `Dn`:** abrir uma trilha de dados para o léxico de sinônimos de ambientes, com fonte por termo (glossários de norma, dicionários, anúncios como evidência de uso) e termos do agente marcados `agente`?
11. **Tabela de intensidade:** aceitar que os valores 1..5 dos modificadores ("perto" = 3, "o mais longe possível" = 5, "não quero perto" = far 3…) são decisão de projeto? O responsável calibraria pontuando ~30 frases, e esse registro seria a "fonte" da tabela.
12. **Conjunto de teste:** tamanho (proposta: ~100–150 dev + ~50 teste reservado por semente), quem escreve as sementes (o responsável, o agente ou ambos) e se paráfrases geradas por modelo maior são permitidas (marcadas e revisadas, nunca no split de teste)?
13. **Barra de qualidade:** que acerto exato por pedido, ou F1 de relações, no split de teste basta para aprovar um modelo? A comparação "regras sozinhas × regras + LLM" entra como critério de que o LLM vale a pena?
14. **Modo sem LLM:** aceitar o modo degradado (resíduo mostrado como "não interpretado", relação criada à mão) como comportamento oficial do app quando o modelo não está instalado ou falha?
15. **`rapidfuzz`:** aceitar como dependência opcional para tolerar erros de digitação ("cosinha", "banhero"), ou começar só com a biblioteca padrão e uma lista de grafias comuns no léxico?
